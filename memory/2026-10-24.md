## 🔴 重大发现：脱敏 sed 误伤标识符，17 个脚本变量名被改坏（21:20 发现并修复）

### 触发
跑 `scripts/health-check.sh` 时报：
`line 255: 已移除: syntax error: operand expected (error token is "已移除")`

### 根因
`claw-mesh-sync.sh` 的全仓库脱敏用了这个 pattern：
```bash
sed -i -e 's/gh[p]_[A-Za-z0-9]*/[已移除]/g' \
       -e 's/sk[_]_[A-Za-z0-9]*/[已移除]/g' ...
```
`sk[_]_[A-Za-z0-9]*` 会匹配到 **`di`sk[_]_**`usage` 里的 `sk_` →
`disk_usage` 变成 `di[已移除]`，`task` 变成 `ta[已移除]`，
`docker_disk_usage` → `docker_di[已移除]`。
**而且这些损坏被 commit 进了共享仓库**（bot5 的 `0e84761d38` 同步提交，2026-10-22 11:20）。

### 影响面
全仓库统计损坏标识符出现次数：
| 损坏形式 | 次数 |
|---------|------|
| `ta[已移除]` (task) | 135 |
| `di[已移除]` (disk) | 25 |
| `update_ta[已移除]` | 10 |
| `docker_di[已移除]` | 4 |
| `bot6_ta[已移除]` / `execute_ta[已移除]` / `agent_ta[已移除]` | 7 |
共 **17 个 shell 脚本**被改坏，脚本直接语法错误无法运行。

### ✅ 修复
1. **改正脱敏 pattern**（3 处：live 脚本 + 仓库 deploy 副本）：
   ```bash
   # 旧: s/sk[_]_[A-Za-z0-9]*/[已移除]/g     ← 会误伤 disk_usage / task
   # 新: s/(^|[^A-Za-z0-9_])sk-[A-Za-z0-9_-]{20,}/\1[已移除]/g
   #    s/(^|[^A-Za-z0-9_])gh[p]_[A-Za-z0-9]{20,}/\1[已移除]/g
   ```
   关键点：**用 `sk-` 连字符而非 `sk_`**（OpenAI key 实际格式就是 `sk-`），
   且要求 ≥20 位 + 左侧不是标识符字符。
2. **从父提交恢复 17 个脚本**：`git checkout 0e84761d38^ -- <files>`
3. 恢复后**只单独脱敏密码**（`[已移除]` → `[已移除]`），不碰标识符
4. `bash -n` 全部 17 个脚本语法检查通过
5. 实跑 health-check.sh，确认不再有 `syntax error` / `integer expression expected`（已移除）
6. 同步修好 `grep -rlE` 的文件定位 pattern（原来 `sk[_]_[A-Za-z0-9]{20,}` 找不到真 token）
7. 已推送：`0dc95dcc1b`

## 🔴🔴 20:00 巡检发现：数据静默丢失（最严重的一次）

### 症状
bot2 的 20:00 同步日志全是成功：
```

[20:00:07] [WARN] rebase 冲突，放弃本地提交并以远端为准
[20:00:14] [INFO] ✅ 同步完成
```
**但仓库里根本没有 `0ff6baac71` 这个提交** —— `bot2/memory/claw-mesh-state.json`
在远端仍是 16:00 的版本。提交被静默丢弃，脚本却宣布成功。

### 根因（push_with_retry 的回退路径）
```bash
if ! git rebase origin/main; then
    git rebase --abort
    git reset --hard origin/main     # ← 把本节点的提交整个丢掉
fi
```
1. bot5 每 5 分钟推送，bot2 每 4 小时 —— bot2 push 时远端常已前进 → push 被拒
2. rebase 失败（index 脏 / 冲突）→ `reset --hard origin/main`
3. 本节点提交**脱离分支历史**，永远不会进仓库
4. 下一轮 `git push` 返回 "Everything up-to-date" → 退出码 0
5. 步骤 5 照打 "✅ 同步完成"

**双重欺骗**：退出码是 0，日志是成功，内容却没了。

### ✅ 复现与验证（隔离实验，不用真实仓库）
造 pushlab：本地有提交、远端被"其它节点"抢先推进 → push 被拒。
- **旧逻辑**：`reset --hard origin/main` → `merge-base --is-ancestor` 判定 → **提交脱离历史 ❌**
- **新逻辑**：`reset --hard HEAD`（只清工作树，保留提交）→ rebase → push → **远端确实含内容 ✅**

### ✅ 修复（5 节点全部生效）
1. **绝不丢弃本地提交**：rebase 失败只做 `git reset --hard HEAD` + `git clean -fd`（清工作树脏改动），提交保留
2. **重试次数** 3→6 次，bot6 的 `while [ $attempt -lt 3 ]` 也一并对齐
3. **兜底校验**：push 失败后用 `git merge-base --is-ancestor "$local_sha" origin/main` 确认内容是否真的入库；未入库则 `save_state 4 "push_failed"` 并**返回非 0**
4. **步骤 5 加验真**：只有确认 `_HEAD_SHA` 是 `origin/main` 的祖先才打 "✅ 同步完成"；否则标记 `completed_unverified`
5. 日志新增"待推送文件"列表，失败时能立刻知道丢了什么

补丁文件：`/tmp/mesh_patch5.py`（bot2/3/4/5）、`/tmp/mesh_patch5b.py`（bot6，块结构不同）

## 🔴 明文密码"复活"：脱敏 pattern 漏了双4变体

修完 push 静默丢失后复查，发现 3 个文件里明文密码又回来了：
`bot3/MEMORY.md`、`bot3/memory/cluster-health-2026-05-22.md`、`bot6/memory/2026-10-23.md`

**根因**：密码有两个历史变体：
- `ge2099334$ZZ`（当前有效，12 位）
- `ge20993344$ZZ`（**双4**，历史变体）

脱敏 pattern 是 `ge2[0]99334` —— 只匹配单4，
`ge20993344$ZZ` 里第一个 4 后面又跟了个 4，匹配不到 → **原样留在文件里**。

这三个文件是 bot3/bot6 在 16:28~16:37 同步时从各自节点带上来的 ——
它们从没被真正脱敏过。

**修复**：pattern 改为 `ge2[0]9933[0-9]*`（覆盖任意位数的 3/4），
grep pattern 与两处 sed pattern 全部同步，5 节点已生效。

**教训**：脱敏 pattern 必须覆盖**已知的所有历史变体**，而不是只匹配当前值。
写死一个精确字符串，等于给旧变体留后门。
（另一条同类教训：10-24 早上把 `ge2099334` 替换掉时，用的是精确串替换，
同样漏了双4 变体 —— 两次都栽在"只处理当前值"上。）
