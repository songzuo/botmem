## Claw-Mesh 同步链路全面修复 (heartbeat 巡检发现)

### 背景
bot2 的两个 4 小时同步任务**从 2026-03-15 起一直全部失败**（日志 5296 条 ERROR），
每次都是"下载 → 合并失败 → 回滚"，实际从未同步成功过。

### 排查过程

| 节点 | 状态 | 问题 |
|------|------|------|
| bot2 | ❌ | cron 同步任务全部失败；只有只读拉取，无回流 |
| bot3 | ❌ | claw-mesh-sync.sh 的 `MACHINE_NAME` 误写为 `bot4`；`WORK_DIR=/tmp/botmem-upload` 不存在；同步 cron 被注释 |
| bot4 | ❌ | `/tmp/botmem-upload/botmem` 内容停留在 2026-05；无同步 cron 实体条目 |
| bot5 | ❌ | 本地 git clone **分叉 65454 个提交**，`git pull --rebase` 从 2026-09-21 起每 5 分钟失败一次 |
| bot6 | ⚠️ | 唯一能正常 push 的节点，但同步 cron 被注释（2026-09-21 停用），靠手动触发 |

### 根因
1. **路径漂移**：bot2 的 `sync-from-slave.sh` / `sync-from-peer.sh` 依赖上游节点的
   `/tmp/botmem-sync/botmem`，但上游已迁移到 `/tmp/botmem-upload/`，且该目录会被清理
   → `远程目录不存在` → 合并失败 → 回滚。
2. **stdout 污染**：`select_sync_node()` 用 `echo "$node"` 返回主机名，但函数内
   `log_info` 用 `tee -a` 把日志写进 stdout，返回变量被污染成整段日志文本
   （日志里可见 `ssh: Could not resolve hostname [2026-10-22`）。
3. **git 仓库污染**：bot5 的 clone 提交了 7.5 万个文件（含 `node_modules`），
   且本地历史与 origin 分叉 65454 个提交 → rebase 永久失败。
4. **凭据失效**：全局 `~/.git-credentials` 里存的 `[已移除]...` token 已失效，
   且配置了 `url.insteadof` 全局改写规则，导致所有 `https://github.com` 克隆
   都自动带上失效 token → `could not read Password` 推送失败。

### bot2 watchdog 的根本 bug（第二次巡检发现）
`/root/.openclaw/cron/claw-mesh-watchdog.sh` 用
`pgrep -f 'claw-mesh-sync'` 判断同步是否存活，但 claw-mesh-sync 是**每4小时一次的
一次性 cron 脚本**，两次运行之间进程根本不存在 → 检查永远失败 →
每5分钟空跑3次"重启"（start_cmd 只是 `echo "Manual trigger required"`，什么也没做）
→ 状态被永久写成 `degraded`，并刷出大量无意义日志。
`MACHINE_NAME` 也误写成 `bot4`。

修复：
- `PROCESSES` 里删掉 `claw-mesh-sync` 这一条（它不是常驻进程）。
- 新增 `check_sync_freshness()`：改为检查"最近一次同步是否成功且新鲜"
  ——同步成功后由 `claw-mesh-sync.sh` 写入 `/var/run/claw-mesh-sync.ok` 时间戳，
  watchdog 比对阈值 6 小时（4小时周期 + 2小时余量）；没有标志文件时退化为解析
  state 里的 `lastSync`。
- `MACHINE_NAME` 改为 `bot2`。

修复后 watchdog 输出 `✅ 所有进程运行正常`，state 为 `healthy`，
日志不再刷屏。

### 第六轮：bot4 SSH 反复掉线的真正根因（安全规则误伤）

**现象**：bot4.szspd.cn 一天内 SSH 掉线 3 次（10:35-10:47、11:26-11:31、15:07-15:10）。
表现为主机 ping 通、22 端口连接超时，而 sshd 服务本身是 active 的。

**排查过程**：
1. 排除资源问题：load 0.01、内存可用 951M、磁盘 75%、sshd active
2. sshd 日志里有大量公网爆破：`Failed password for invalid user admin/hwm/cisco`
   来自 34.78.14.134、113.211.192.150、171.244.142.205、191.7.159.201 等
3. bot4 的 iptables 里有**两条重叠的 SSHLIMIT 规则**：
   ```
   -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -m recent \
       --update --seconds 60 --hitcount 4 --rttl --name SSHLIMIT -j DROP
   -A INPUT -p tcp --dport 22 -m conntrack --ctstate NEW -m recent \
       --update --seconds 60 --hitcount 5 --rttl --name SSH -j DROP
   ```
   同一源 IP **60 秒内连接 4 次即被 DROP**
4. 关键点：规则按**源 IP** 计数，而集群节点之间是同一源 IP 反复连接
   （尤其是 SSH 失败后的重试）→ **正常节点被自己的防护规则静默封掉**
5. 实测：等待 70 秒让计数窗口过期后即可正常连上，证实就是这条规则

**注意**：bot3 也有同样的 SSHLIMIT 规则，bot5/bot6 没有。
bot4 上原有的 `47.81.39.226 ACCEPT` 规则是给 **18789 端口**（网关）的，
**不覆盖 22 端口**，所以之前一直以为已经放行了。

**修复**：新增 `/usr/local/sbin/allow-cluster-ssh.sh`
- 把 5 个集群 IP 的 22 端口 ACCEPT 规则插入到 INPUT 链**最前面**
  （必须在 SSHLIMIT DROP 之前命中，否则无效）
- 幂等：先删旧规则再插入
- 持久化：`/etc/iptables/rules.v4` + systemd unit
  `iptables-clawmesh.service`（enabled）+ `/etc/rc.local` 兜底
- 部署到 bot3、bot4

**验证**：修复前 8 次快速连接 0/8 成功，修复后 bot4 与 bot3 均 **8/8 成功**。

### 第七轮：bot6 时区错配（Europe/Berlin）

**现象**：bot6 的 `lastSync` 显示 08:30，而集群其他节点都是 15:xx，差 6 小时。
其自身日志时间也一直偏早（当时真实时间 10:48，日志却写 04:48）。

**排查**：`date` 显示 bot6 为 `CEST / Europe/Berlin`，其余节点均为 `CST / Asia/Shanghai`。
不是环境变量污染，是 `/etc/localtime` 符号链接和 `/etc/timezone` 就是这么配的。
epoch 时间戳一致，所以 watchdog 的新鲜度判断和定时任务本身都没出错，
只是**所有展示时间与共享仓库里的提交信息都偏了 6 小时**。

git log 佐证：
```
0e84761d38 2026-10-22 11:20:04 +0800 bot5: ...
707948ea7b 2026-10-22 04:48:17 +0200 bot6: ...
```

**修复**：
```
ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime
echo 'Asia/Shanghai' > /etc/timezone
```
修复后 bot6 时间 15:16:13 CST，watchdog 与同步均正常，
`lastSync` 刷新为 `2026-10-22 15:16:37`。

**教训**：跨机集群排查时，先对齐时钟/时区，否则时间戳类证据会指向错误方向。

- 已改为**白名单**：只同步 `HEARTBEAT.md` 与 `docs/CLAW-MESH-HANDOVER.md`
- 已清理仓库中 `static/docs/` 的 317 份文件，恢复为 1 份

**推送被拒无法自愈**：
bot4 报 `! [rejected] ... (fetch first)` 后退出。原因是脚本用
`git pull --rebase` 一条命令完成 fetch+rebase，fetch 卡住时 rebase 一直等待，
且**状态停在 step 4**（push），下次运行会**跳过拉取步骤**直接再失败。
- 新增 `push_with_retry()`：push 被拒 → fetch → rebase → 重试（最多 3 次），
  rebase 冲突则放弃本地提交以远端为准
- bot4 的 `upload-botmem.sh` 同样改造

**陈旧状态自愈**：
`load_state` 增加判断——若 step>0 且上次更新超过 1 小时，视为异常中断残留，
重置为从头同步。（bot3 曾在 step 4 卡了 3.7 小时）

**bot3 弱网**：
bot3 到 github.com 的链路**间歇性丢包**（实测 5 次请求仅 2 次成功），
而 api.github.com / codeload.github.com 正常（不同 IP 段）。
排查过程：TCP 握手时通时不通、TLS 停在 "Trying..."、ping 丢包 50%，
但换 IP 无效 —— 确认是链路质量而非 DNS/封锁。
- `MAX_RETRIES` 3 → 5
- fetch 加 `http.connectTimeout=15`、`lowSpeedLimit/Time`，避免 134s 超时拖垮周期
- 拉取改为**分步**执行：`fetch` → `rebase` → `reset --hard`，
  每步独立失败处理，不再用 `git pull --rebase` 一条龙

**凭据统一**（本轮顺带发现）：
- bot4 的 `~/.gitconfig` 里有 **`url.https://[已移除]...@github.com/.insteadof`**
  规则，把所有 github.com URL 改写成**已失效**的 token → push 必然失败
  （与 bot2 当初的故障完全同源）。已删除该规则
- 四台节点统一：`credential.helper=store` + `~/.git-credentials`（600）
  + remote URL 不再内嵌 token

### 第十轮：共享文件被截断为 0 字节

**现象**：仓库里 `static/HEARTBEAT.md` 变成 **0 字节**，各节点拉不到清单。

**根因**：脱敏逻辑与 `cp` 拷贝 `static/` 的**竞态**。
- 脱敏的 `grep -rl ... | while read; do sed -i ...` 会改写整个工作树（含 static/）
- 同一次运行的 `sync_to_github` 又要把 `$BOT4_DIR/HEARTBEAT.md` 拷进 `static/`
- `sed -i`（原地重写）与 `cp`（截断后写入）撞在一起 → 0 字节

**修复**：
1. 脱敏**排除 static/** 目录（它是 cp 的输入，不是输出）
2. cp 改为**临时文件 + mv 原子替换**（`cp → .tmp → mv`）
3. 拉取侧增加 `-s` 非空校验，避免用空文件覆盖本机正常内容
4. 仓库侧已修复 `static/HEARTBEAT.md`

**验证**：bot3/bot4/bot5 的 HEARTBEAT.md md5 已与 bot2 一致；
bot4 的 `docs/` 目录从 317 份污染文件回落到 1 份（白名单生效）。

### 遗留（本轮新增）
- **bot6 SSH 不可达**：主机 ping 通、22 端口不通（与 bot4 早前同样表现），
  本机无 SSHLIMIT 规则（bot5/bot6 都没装），属主机自身 sshd 不稳定。
  bot6 的新脚本已在 20:15 部署到位，恢复了连接后即可自愈。
- bot4 SSH 同样频繁超时，部署脚本时需多次重试。

### 第十一轮：static/ 改为 bot2 独占写入

**问题**：共享清单 `static/HEARTBEAT.md` 反复被"污染成"奇怪内容：
- 一度是 211687 字节 —— 某节点（bot6）把自己的**心跳日志**堆进了清单
- 一度是 0 字节 —— cp 中断截断

**根因（设计缺陷）**：原实现里**每个节点都把自己的 HEARTBEAT.md 推到 static/**。
但各节点的 HEARTBEAT.md 内容并不一致（bot6 的 200KB+ 是日志堆叠），
于是"最后推送的节点"决定仓库里共享清单的内容 —— 谁跑最后一次谁说了算。

**修复**：只有 **bot2** 写 `static/`，其余节点只读。
共享清单由 bot2 统一维护，从根上消除互相覆盖。

**顺带修复**：bot2 工作区的 6 个本地提交曾被我自己的
`git reset --hard origin/main` 误删（reflog 里找回）。
根因是把"同步仓库"和"工作区仓库"当成同一个 —— 实际是两套：
- 同步副本：`$WORK_DIR/botmem`（每次从远端重置，可以随便 reset）
- 工作区：`/root/.openclaw/workspace`（有自己的提交，**不能随便 reset**）

**教训**：在工作区仓库里执行 `reset --hard` 前必须先确认当前 HEAD
不在同步副本路径下。

### 第十二轮：共享路径互相覆盖 + 污染清理收尾

**问题 1：状态文件被别的节点覆盖**

**问题 2：污染文件残留在节点本地**
仓库里已清理，但 bot4/bot5/bot6 的**本地** `docs/` 还留着 305/305/318 份

### 第十三轮：巡检清单八项全过 + 三个新问题

**重要更正**：第八轮里我把 bot4/bot5/bot6 本地 `docs/` 的 305 份文档当成

### 第十四轮：GitHub 路由黑洞 + 自愈固化

**现象**：bot5 的 `git fetch` 永久挂起，状态停在 `step: 1 pulling`，
00:40 的 cron 起就没动过。

**排查**：
- `getent hosts github.com` → `20.205.243.166`
- 该 IP 的 443 端口**完全不可达**（`/dev/tcp` 测试失败）
- `api.github.com`(200) / `codeload.github.com`(301) 正常 ——
  **它们的 IP 段和路由与 github.com 不同，不能据此判断 github.com 可用**
- 逐个测候选 IP（`curl --resolve` 带 SNI）：
  - 可用：`20.27.177.113`、`20.200.245.247`、`20.207.73.82`
  - 黑洞：`20.205.243.166`、`140.82.121.4/114.3/113.4/112.4`
    （这些 IP TCP 能连上但 TLS 握手无响应）

**修复**：`/etc/hosts` 把 `github.com` 钉到可用 IP，git 立即恢复
（`ls-remote` 正常，同步成功）。

**自愈固化**：`github-ip-pin.sh`（每 10 分钟）——
探测 `github.com` 不通时，自动从候选 IP 里挑一个能完成 TLS 的写进
`/etc/hosts`。五台全部部署（bot5 实测有效）。

**另一个隐患**：git 的 `lowSpeedTime` 对"TCP 连上但 TLS 无响应"这种
挂起**无效** —— git-remote-https 会一直等下去。
所以除了超时参数，还必须有外层的 IP 探测。
